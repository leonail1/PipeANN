\section{文档目标}
本文档只保留可实施内容，用于指导 PipeANN 将现有的 hybrid 搜索能力从 \path{hybrid_rebuild_context} 迁移到正式源码树，并在正式接线与验证完成后删除整个 \path{hybrid_rebuild_context} 目录。本文档不再记录代码审查结论，不再区分“已有能力”和“缺失能力”，只定义后续工程实施的目标、模块落点、阈值机制和验证步骤。

\section{实施范围}
本次实施范围限定为以下四项：

\begin{enumerate}
\item 将 hybrid 搜索框架从实验目录迁入正式代码目录，即迁入 \path{include/}、\path{src/} 和 \path{tests/}；
\item 在正式查询接口中新增统一 hybrid 查询入口，使 prefilter 与 graph-only 两条路径由同一套运行时逻辑调度；
\item 将路径切换机制统一为候选规模单阈值 \(\tau_m\)，并在第一次索引构建完成后通过一次轻量 benchmark 生成初始阈值；
\item 将阈值重定位的唯一触发条件定义为向量数量变化超过 10\%，并要求重定位在后台单线程执行，且每条 benchmark 查询开始前都要检测前台负载。
\end{enumerate}

标签变化不作为阈值重定位触发条件。标签更新只负责维护查询时的候选规模计算输入，不负责触发重新 benchmark。

\section{总体实施目标}
本次集成完成后，PipeANN 中的过滤查询应具备如下统一执行流程：

\begin{enumerate}
\item 查询到达正式查询入口；
\item 运行时根据当前过滤条件计算候选规模 \(m(F)=|S_F|\)；
\item 将 \(m(F)\) 与候选规模阈值 \(\tau_m\) 进行比较；
\item 若 \(m(F)\le \tau_m\)，则进入 prefilter 路径；
\item 若 \(m(F)>\tau_m\)，则进入 graph-only 路径；
\item 两条路径共用同一套索引前缀、标签 sidecar、查询统计接口和测试入口。
\end{enumerate}

对应的路由规则定义为
\[
m(F)=|S_F|,
\]
\[
m(F) \le \tau_m \Rightarrow \text{prefilter},
\qquad
m(F) > \tau_m \Rightarrow \text{graph-only}.
\]

\section{统一 hybrid 查询入口}
统一 hybrid 查询入口建议作为正式查询接口的一部分实现，而不是继续保留为脚本层的路径分发。该入口需要完成以下工作：

\begin{enumerate}
\item 接收查询向量、过滤表达式、\texttt{k}、\texttt{L}、\texttt{beamwidth} 等正式参数；
\item 基于当前过滤表达式计算候选规模 \(m(F)\)；
\item 将 \(m(F)\) 与当前阈值 \(\tau_m\) 比较，并记录本次选路结果；
\item 当选择 prefilter 路径时，若已有 bitset 中间结果，则直接复用；
\item 当选择 graph-only 路径时，直接复用现有 \texttt{pipe\_search(..., selector, filter\_data, ...)}；
\item 向统一统计接口输出路径选择、候选规模、阈值版本和查询耗时。
\end{enumerate}

\section{候选规模计算机制}

\subsection{单标签查询}
对于单标签查询，正式实现中建议维护每个标签的 live 候选数。若迁移初期仍沿用已有的选择性表，则可按
\[
m(F)=\rho(F)\cdot N_{\text{live}}
\]
换算出候选规模；当正式元数据补齐后，运行时直接读取该标签的 live 候选数即可。无论使用哪种表示，路由比较对象都统一为 \(m(F)\)，而不是直接比较选择性。

\subsection{多标签交集查询}
对于多标签交集查询，即要求结果向量至少包含查询中的全部标签，运行时在 DenseBitset sidecar 上执行按位与，再对结果做 \texttt{popcount}，得到不重复候选数：
\[
m(F)=\left|\bigcap_{\ell \in F} S_{\ell}\right|.
\]

若最终选中 prefilter 路径，则复用同一份 bitset 结果继续物化候选 ID；若最终选中 graph-only 路径，则只保留计数结果参与路由，不额外物化 ID 列表。

\subsection{多标签并集查询}
对于多标签并集查询，运行时在 DenseBitset sidecar 上执行按位或，再对结果做 \texttt{popcount}，得到去重后的候选规模：
\[
m(F)=\left|\bigcup_{\ell \in F} S_{\ell}\right|.
\]

这里同样遵循“先计数后选路”的原则。只有在最终选中 prefilter 路径时，才将 bitset 结果物化为候选 ID 列表。

\section{阈值初始化与持久化}

\subsection{初始阈值生成}
第一次索引构建完成后，系统立即执行一次轻量 benchmark，用来生成初始候选规模阈值 \(\tau_m\)。该 benchmark 仅服务于阈值标定，不承担实验作图职责，要求如下：

\begin{enumerate}
\item 使用单线程执行，避免与前台检索竞争资源；
\item 在一组代表性过滤查询上分别运行 prefilter 与 graph-only；
\item 记录两条路径在相同检索参数下的延迟；
\item 找到两条成本曲线的交叉区间，并输出一个初始候选规模阈值 \(\tau_m\)；
\item 将 \(\tau_m\)、标定时的 live 向量总数 \(N_{\text{calib}}\) 以及标定时间持久化为正式元数据。
\end{enumerate}

\subsection{阈值元数据}
建议在正式元数据中增加以下字段：

\begin{enumerate}
\item 当前候选规模阈值 \(\tau_m\)；
\item 上一次标定时的 live 向量总数 \(N_{\text{calib}}\)；
\item 当前 live 向量总数 \(N_{\text{live}}\)；
\item 阈值版本号与上次标定时间；
\item 阈值是否处于待重定位状态的标志位。
\end{enumerate}

\section{阈值重定位机制}

\subsection{唯一触发条件}
阈值重定位的唯一触发条件定义为 live 向量总数相对上一次标定时的向量总数发生超过 10\% 的变化。触发条件写为
\[
\frac{\left|N_{\text{live}}-N_{\text{calib}}\right|}{N_{\text{calib}}} > 0.10.
\]

除这一条件外，不再引入任何其他自动触发条件。标签变化不触发阈值重定位，维护事件也不单独触发阈值重定位。

\subsection{后台重定位执行方式}
当触发条件成立后，系统只做两件事：

\begin{enumerate}
\item 将阈值状态标记为待重定位；
\item 在后台启动单线程轻量 benchmark，重新生成新的 \(\tau_m\) 并更新 \(N_{\text{calib}}\)。
\end{enumerate}

后台重定位期间，前台查询继续使用旧阈值工作，待新阈值生成并持久化后再切换。

\subsection{前台负载检查}
每条后台 benchmark 查询开始前，都必须检查一次前台负载。若前台处于高负载，则本条 benchmark 查询不执行，后台任务暂停并等待下一个空闲窗口。前台负载检查建议至少包含以下条件：

\begin{enumerate}
\item 当前前台查询并发低于低水位；
\item 查询等待队列为空或接近空；
\item 当前没有正在执行的前台高优先级维护任务；
\item 当前没有用户显式禁止后台重定位。
\end{enumerate}

\section{更新路径配套要求}
由于系统支持更新，更新路径需要同时维护路由输入与阈值元数据：

\begin{enumerate}
\item 插入与删除操作必须更新 live 向量总数 \(N_{\text{live}}\)；
\item 插入、删除和标签变更必须更新 DenseBitset sidecar 对应的 live 状态，保证 \(m(F)\) 的查询期计算正确；
\item 标签变化只更新候选规模计算输入，不触发阈值重定位；
\item 每次更新完成后都要检查一次是否满足 10\% 的向量数量变化阈值；
\item 若满足条件，则仅设置后台重定位任务，不阻塞前台查询路径。
\end{enumerate}

实现完成后，至少执行以下验证：

\subsection{构建与集成验证}
\begin{enumerate}
\item 主工程 \path{src/CMakeLists.txt} 能成功编译包含 \path{filter/*.cpp} 的正式库；
\item 正式测试驱动可以直接调用统一 hybrid 查询入口；

\item 删除 \path{hybrid_rebuild_context} 后，仓库仍能完成构建与核心验证。
\end{enumerate}

\subsection{路由正确性验证}
\begin{enumerate}
\item 单标签查询可基于 live 候选规模正确选路；
\item 多标签交集查询可通过 bitset 按位与加 \texttt{popcount} 正确计算 \(m(F)\)；
\item 多标签并集查询可通过 bitset 按位或加 \texttt{popcount} 正确计算 \(m(F)\)；
\item 路由决策日志中能看到 \(m(F)\)、\(\tau_m\) 和最终路径选择。
\end{enumerate}

\subsection{阈值重定位验证}
\begin{enumerate}
\item 当 \(N_{\text{live}}\) 与 \(N_{\text{calib}}\) 的差值超过 10\% 时，后台重定位任务被正确触发；
\item 后台重定位始终以单线程执行；
\item 每条后台 benchmark 查询前都执行前台负载检查；
\item 当负载检查失败时，后台任务能暂停并在后续继续；
\item 阈值更新后，\(\tau_m\) 与 \(N_{\text{calib}}\) 被正确持久化。
\end{enumerate}
