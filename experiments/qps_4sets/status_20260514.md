## GloVe100 Diagnosis

The original `glove100` formal sweep appeared stuck at `u0p1/t1` for over 37 minutes. The disk index itself was valid: non-hybrid search completed quickly, and the base/query vectors were finite and normalized.

Root cause: the hybrid benchmark was missing the densebit sidecar and hybrid metadata for the GloVe index. In `auto` mode, `hybrid_search` fell back to graph search while still applying the label selector. At very low selectivity that graph-filter fallback is extremely slow, which made the run look hung.

Fix: generate densebit sidecars and minimal hybrid metadata for all four datasets, then rerun the formal sweep with the original low-memory benchmark semantics restored. Representative GloVe revalidation after the fix showed `hybrid_enabled=true`, `prefilter_count=1000`, `fallback_count=0`, and QPS around 1.4k-1.5k for `u0p1/t1`.

## Bottleneck Summary

The external CPU/SSD sampler did not observe sustained NVMe device saturation in this run: sampled disk utilization and read throughput are effectively zero in the tracked summary columns. That is not sufficient evidence to conclude that every high-selectivity graph-search point is purely CPU-bound. The thread-scaling plot shows clear non-linear scaling, especially in the graph-search region, so the safer conclusion is that the measured run is not visibly limited by whole-device NVMe throughput, while graph search still appears constrained by some combination of CPU, memory/cache behavior, random I/O latency hidden below coarse device sampling, and per-query synchronization/algorithmic overhead.

The new scaling-efficiency plot is the main evidence for this caveat. For example, the 8-thread-vs-1-thread efficiency in high-selectivity graph-search buckets is roughly 0.67-0.78 on GIST/GloVe/YFCC rather than 1.0, so QPS does not increase linearly with CPU threads.
