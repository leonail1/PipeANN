## Current Long-Running GloVe100 Run

The formal `glove100` sweep started at `u0p1/t1` with:

```text
search_disk_index_hybrid float data/glove100/glove100_qps4_pipeann 1 4 ... u0p1/queries.spmat auto 0 0 100
```

Observed state:

- The process remained in `R` / CPU-running state for over 30 minutes.
- CPU stayed near 120% for a nominal single-thread run, with two process threads visible.
- `/proc/<pid>/io` showed very low read bytes, so the run was not waiting on SSD bandwidth.
- Output JSONL is written only after the full query batch finishes, so no intermediate `auto.jsonl` file is expected while the binary is still running.
- `gdb` attach was blocked by Linux ptrace policy (`Operation not permitted`), so user-space stack capture was not available without changing system policy or running as root.

Interpretation: this does not look like an SSD bottleneck. It is either an extremely expensive CPU-bound low-selectivity `auto` search path for GloVe100 or a compute-side loop in that path. The process is still consuming CPU rather than sleeping or waiting on IO.

## Git Hygiene

Large generated files are intentionally left out of Git:

- `data/*`
- `experiments/**/*.bin`
- `experiments/**/*.spmat`
- `experiments/**/*.index`
- `experiments/**/*.densebit`
- bulky generated scan/detail JSONL files such as `single_label_label_stats.jsonl` and runtime label summaries

Compact manifests, summaries, plots, and aggregated result tables are kept trackable.
